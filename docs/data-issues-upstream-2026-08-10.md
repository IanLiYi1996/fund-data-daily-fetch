## P1 规模表停止同步（`fund_scale_history.parquet`）

**反馈**：2026-06-30 报告期几乎为空；规模是清盘风险（净资产 < 2 亿）的唯一判断依据，
当前仍停在 3/31 数据，已滞后 4 个多月。

**诊断**：调度时点错误，非采集失败。

- 文件最后写入 `2026-07-04`（对比经理表 08-09、持仓表 08-04）
- `FundScaleHistoryQuarterlySchedule` = `cron(0 19 4 1,4,7,10 ? *)`，即
  **1/4/7/10 月的 4 号**
- 代码注释写的是"quarter end 后 3 天缓冲，多数季度数据已发布" ——
  **这个前提是错的**：基金季报的法定披露期限是季度结束后 **15 个工作日**，
  7 月 4 号那次运行根本看不到 Q2 数据
- 实测 `2026-06-30` 报告期在表里只有 **30 只**，而表内共 26,646 只
- 上游 `pingzhongdata.js` 的 `Data_fluctuationScale` **已有 Q2 数据**
  （抽验 110022 = 97.06 亿、110011 = 67.77 亿、017641 = 53.03 亿）

对比：`FundPortfolioHoldQuarterlySchedule` 用的是 25 号（`cron(0 20 25 1,4,7,10 ? *)`），
留了约 3 周披露缓冲 —— 持仓表因此正常，规模表因此落空。

**修复**：`cron(0 19 4 1,4,7,10 ? *)` → `cron(0 19 25 * ? *)`

改成**按月**而非按季，是刻意的：按季意味着一个披露窗口只跑一次，单次运行出问题
就要等下一个季度才有机会自愈 —— 这次就是如此，一次落空导致 4 个月陈旧。按月跑
让漏掉的窗口在 30 天内自动补上，且调用的是每周经理刷新已经在用的同一个端点，
量级上没有新增风险。

外加一次性回补 2026-06-30 报告期，**已完成并验证**：

| | 前 | 后 |
|---|---|---|
| 总行数 | 122,250 | 126,178 |
| 基金数 | 26,646 | 26,984 |
| **报告期 2026-06-30** | **30 只** | **25,861 只** |

跨账号复制状态 `COMPLETED`，已送达消费方。

## P2 经理表 958 只基金记录消失

**反馈**：26,736 只有 2026-08 净值的基金中，958 只在 `fund_manager_history.parquet`
里零记录。分布：其他 316、指数/ETF 297、债券 186、FOF/持有期 104、货币 38、QDII 17。
举例 110022 易方达消费行业股票（净值到 8/7，Q1 规模 126.86 亿）、
017641 摩根标普500指数(QDII)人民币A。

消费方判断：**自动化测试一直断言 110022 任期非空并通过，8/10 才开始失败，
怀疑是 8 月上旬某次更新误删，而非从未采集。**

**诊断：这个判断是对的 —— 但不是"删除"操作，而是覆盖写没有保留上一版记录。**

链路上有两个缺陷叠加：

| 环节 | 行为 | 后果 |
|---|---|---|
| 抓取 | 4 分片并发抓 `fundf10.eastmoney.com/jjjl_{code}.html`，重试 3 次、退避 0.5s/1.0s | 上游返回 `HTTP 514 Frequency Capped`，失败基金静默计入 `error_count` 后跳过 |
| merge | `pd.concat(本周 part 文件)` 后**整体覆盖**规范文件 | **本周被限流的基金从文件里消失** |

2026-08-09 那次运行 `error_count = 1008`（universe 约 27.5k），与反馈的 958 只
基本吻合；错误样本里能直接看到 `017641`。

关键点：**上游数据一直是好的**。用我们自己的解析器直接抓这三只，
110022 解析出 10 行任期、110011 出 4 行、017641 出 1 行 —— 解析器无问题，
纯粹是抓取被限流 + 覆盖写丢弃。

而且这个缺陷**每周都在掷骰子**：每周随机约 1,000 只基金从文件里消失，
只是这次刚好砸中消费方测试用的 110022。经理表滞后不是单点事故，是结构性缺陷。

**修复**：

1. **merge 改为与上一版求并集**（`_carry_forward`）。粒度是**基金**而非行：
   本次抓到的基金，其历史被整体替换（每次都是全量重抓，本次即权威）；
   本次没抓到的基金，保留上一版记录。行级 concat+dedup 是错的 ——
   会把上游已经修正/撤销的任期记录复活。
   读取上一版失败时直接抛错，绝不退化成覆盖写。
2. **限流感知重试**：识别 514/429/503 与 `Frequency Capped`，
   退避基数 1.5s 指数递增 + 抖动（避免整个线程池同步重试再次触发限流），
   重试次数 3 → 5。
3. **截止时间保护**：剩余调用时间不足 90s 时不再 sleep。
   实测数据支撑这个取舍 —— 100 只真实 code 在 32 并发下 **零 514**，
   说明限流是全量跑到中途的累积突发（1,008/27,479 = 3.7%），
   而非并发上限；所以降并发无用，而朴素指数退避会撑爆 15 分钟上限
   （1,008 只 × 14s ÷ 8 workers ≈ 1,760s）。既然 merge 已经会保留记录，
   放弃一只基金的代价是一行陈旧数据，而不是一条被删除的记录。

回归测试：`tests/unit/test_fund_history_handler.py` 3 个（限流基金不消失、
已刷新基金整体替换、首次 merge 无历史可继承）+
`tests/unit/test_fund_history_fetcher.py` 2 个（限流退避长于瞬时错误、
退避尊重截止时间）。

**已完成并验证**：

| | 前 | 后 |
|---|---|---|
| 总行数 | 126,395 | 131,195 |
| 基金数 | 26,299 | 27,287 |
| **恢复基金数** | — | **988** |
| 110022 易方达消费行业股票 | 0 行 | **10 行** |
| 017641 摩根标普500指数(QDII) | 0 行 | **1 行** |

限流效果对比：同一分片结构下 `error_count` 合计 **1,008 → 19**（降 98%）。
跨账号复制状态 `COMPLETED`，已送达消费方。
110022 的任期断言现在应当恢复通过。

## P3 "有行但值等于前一交易日" 的语义

**反馈**：请确认这是否意味着当日真实净值尚未披露（T+1）。
2026-08-03 有 94.2% 与 7/31 完全相同，次日回落到 3.6%。

**结论：不是 T+1，不要把它编码成"预期行为"。94.2% 是真实缺陷，且已修复。**

这一条要说清楚，因为把它当作正常现象会让你们的健康检查漏掉一个有效信号。

实测（2026-08-10 在当前数据上重新量测，判定为两日净值**完全相等**）：

| 日期对 | 相同占比 |
|---|---|
| 07-30 vs 07-29 | 4.7% |
| 07-31 vs 07-30 | 4.1% |
| **08-03 vs 07-31** | **6.4%** |
| 08-04 vs 08-03 | 4.5% |
| 08-05 vs 08-04 | 10.0% |
| 08-06 vs 08-05 | 8.7% |
| 08-07 vs 08-06 | 3.7% |

两点：

1. **健康基线是 4–10%**，不是 94%。少量相同属正常 —— 货币基金当日零波动、
   停牌份额、净值精度截断都会造成相等。
2. **你们引用的那一对现在是 6.4%**。94.2% 是你们取样时的状态；
   之后 08-03 整日数据已从上游重抓改写，所以现在落在基线内。
   次日"回落到 3.6%"不是自然收敛，是那次改写的结果。

所以：**大比例前值结转是可用的缺陷信号，建议纳入你们的健康检查而非豁免。**
阈值建议 20%（基线上限 10% 的两倍），超过即告警。

### 什么才是真正的 T+1 合法现象

不是"值等于前一日"，而是这两个：

- **行存在但净值为 NULL** —— 每日约 700–1,400 只（占 2.7–5.2%）。
  ETF、货币基金按 T+1 披露，QDII/FOF 更慢（要等境外市场结算）
- **最新一天覆盖率偏低** —— 最新一天约 89%，往回一天 98.3–99.9%

因此**新鲜度检查应当评估"上一个已结算交易日"，而不是最新一天**，
否则每天都会误报。我们自己的 `_check_coverage` 就是这么做的
（`target = trading[-2]`）。

**注意**：行存在但值为 NULL 属正常披露节奏；但如果某只基金**上游有值而我们写了
NULL**，那是缺陷 —— 就是已修复的 684 只 T+1 产品问题
（写入时按整帧而非按行选择净值列）。这两者的区别要靠与上游对账才能分辨，
我们每日心跳里的抽样对账做的就是这件事。

## 附带发现并修复：08-06 / 08-07 净值写 NULL

上线新监控后当场触发，是这次排查的额外收获（不在原反馈里）：

- 每日心跳报"我们缺少 31 个日期（上游有）"，上游对账掉到 129/160
- 逐个核对后分两类：
  - `023455@2026-08-10` **不是缺口** —— 当天采集还没跑（cron 17:00 UTC）
  - `026605` / `019661` 等 **@08-06、08-07 是真缺陷** —— 我们写了 NULL，
    上游有值（0.9913 / 1.2959）
- 根因：08-08（周六）那次 fallback 目标日算成周末却按全量 universe 求差集
  （27,479 只），**900s 超时**，把后续几天拖坏。周末只抓货币基金的修复
  （commit `139fa68`）当时**已在 git 但尚未部署**，今天这次部署才生效
- 已回补：08-06 补 424 只、08-07 补 420 只，抽验值与上游完全一致

**教训**：`139fa68` 提交后没有立即部署，代码库与运行环境不一致了几天。
监控看的是运行结果而不是提交历史，所以是监控发现了它 —— 这正说明
新增的历史文件检查值得做。

注：fallback 是 append 语义，补进来的好行与原 NULL 行并存，
Iceberg 内部会暂时同时有两行。消费方读的扁平导出已按
`ORDER BY CASE WHEN unit_nav IS NOT NULL THEN 0 ELSE 1 END` 去重，
拿到的是真实值；每周 compaction 会清掉 NULL 行。

### 又一个自查误报：对账窗口用了墙上时钟

修完上面之后，心跳仍报"缺少 144 个日期（上游有）"、对账掉到 30/160，
但**全部是 `@2026-08-10`** —— 也就是当天还没采集的数据。根因在
`reconcile()` 里 `hi = date.today()`：采集在 17:00 UTC 才跑，
任何早于该时刻的检查都会把一整天算成缺失。**拿我们从未声称拥有的日期
去对账，不是缺陷信号。** 改为 `hi = _latest_loaded_date(catalog)`。

修完后对账 30 → 125/160，剩下的才是真缺口。继续用 fallback 回补：
08-06 补 520 只、08-07 补 320 只、08-09（周日货币基金）补 379 只。

## 补充：255 只滞后 > 5 天，与生命周期状态字段

**反馈**：5–30 天 99 只、30–90 天 139 只、> 90 天 17 只；
消费方无法区分"停更"与"已终止"，建议增加状态字段。

**回应：建议合理，且我们已有基础设施可以直接支撑。**

现有 `fund_inactive` 表（`fund_code` / `reason` / `last_seen_date` / `verified_at`）
由 freshness-check 每天自动维护：

- **age in**：连续 30 天无 `fund_daily` 行，且上游 `lsjz` 也无序列 → 判为不活跃
- **age out**：重新出现在 `fund_daily` → 立即移出（恢复的基金不能对覆盖率检查隐身）

之所以做成从数据推导而非手工维护：手工名单会腐坏 —— 曾有"约 900 只货币基金缺失"
的估算在 issue 里躺了几周，而 fallback Lambda 早已把它修到只剩 29 只，
那个陈旧数字带着一整个 spike 走错了方向。

已确认的上游终止情况（spike 实测 714 只缺口）：
REITs 71 只最后数据点在 2024-03 ~ 2025-10（已摘牌/转让）、
QDII 美元现汇份额三源否证（境外计价份额不在境内基金页面披露）。

**已做**：新增 `fund/_history/fund_lifecycle.parquet`（复制状态 `COMPLETED`），
覆盖**全部 27,479 只** universe —— 不只是豁免名单，因为消费方要为每个 code
拿到判定，"文件里没有"不是可筛选的答案。

列：`fund_code` / `fund_name` / `fund_type` / `last_nav_date` / `lag_days` /
`status` / `as_of`。`last_seen_date` 之前 653 行**全为空**，正是消费方判断
"停更多久"缺的那个字段，现已填充。

`status` 五个取值（当前分布）：

| status | 只数 | 含义 / 消费方应如何处理 |
|---|---|---|
| `active` | 26,770 | 30 天内有披露，正常使用 |
| `terminated` | 648 | 已探测确认上游无序列 —— 清盘/摘牌，**剔除** |
| `presumed_terminated` | 31 | 静默超 1 年但未探测 —— **建议剔除** |
| `stalled` | 21 | 停更但仍可能恢复（定开/持有期）—— **保留** |
| `never_reported` | 9 | 在 fund_name 但从未产生净值 |

判定依据是**上游是否仍有序列，而不是静默时长** —— 3 个月持有期 FOF 可以
合法静默 90 天，单靠时长会把活着的产品判死。

**`presumed_terminated` 这一档是测量逼出来的**：最初只做 stalled/terminated
二分，结果 52 只未探测的静默 code 里 **31 只静默超过一年**（最长 3,603 天
≈ 10 年）被标成"可能恢复"。让消费方保留 10 年不动的基金比不给判定更糟，
但我们也没确认它死了，所以单独一档。修正后 `stalled` 只剩 21 只，
实测样本是 32–160 天的定开债 —— 这才是"可能恢复"的真实形态。

阈值 `PRESUMED_DEAD_AFTER_DAYS=365` 可通过环境变量覆盖。
